# RFC-0023 — Context Builder

**RFC Number:** RFC-0023

**Title:** Context Builder

**Status:** Approved

**Version:** 1.0.0

**Authors:** ForgeOS Architecture Office

**Last Updated:** 2026-08-01

---

# Abstract

This RFC defines the Context Builder, the subsystem responsible for constructing deterministic, explainable, and mission-specific execution context for every Professional within ForgeOS.

The Context Builder ensures that every decision, recommendation, and execution activity is grounded in authoritative organizational knowledge rather than temporary conversation history or provider-specific memory.

Context is treated as a derived organizational artifact rather than an implementation detail.

---

# Motivation

Modern AI systems typically rely upon:

* conversation history,
* prompt engineering,
* provider memory,
* vector similarity,
* user instructions.

These mechanisms are implementation-specific and frequently produce inconsistent reasoning.

ForgeOS instead constructs context from governed organizational assets.

Professionals should receive the right knowledge rather than the largest possible context.

---

# Problem Statement

Without deterministic context construction:

* recommendations become inconsistent;
* organizational standards are ignored;
* architectural decisions are forgotten;
* duplicate reasoning occurs;
* token usage increases unnecessarily;
* explainability is reduced.

Context should therefore be intentionally engineered rather than passively accumulated.

---

# Goals

The Context Builder shall:

* construct deterministic execution context;
* prioritize authoritative knowledge;
* minimize irrelevant information;
* support explainable reasoning;
* remain AI-provider independent;
* optimize organizational learning.

---

# Non-Goals

The Context Builder does not define:

* embedding models;
* vector databases;
* prompt templates;
* LLM providers;
* inference execution;
* caching strategies.

Those concerns belong to implementation specifications.

---

# Decision

ForgeOS introduces the Context Builder as the exclusive subsystem responsible for constructing execution context.

No Professional, Mission, Executive Meeting, or AI Provider shall independently assemble organizational context.

Context construction is centralized to preserve consistency and governance.

---

# Context Principles

## Knowledge Before Conversation

Permanent organizational knowledge always has higher priority than temporary conversations.

---

## Authority Before Recency

Authoritative documents outrank recently created but unvalidated information.

---

## Relevance Before Volume

Smaller, highly relevant context is preferred over large, unfocused context.

---

## Explainability Before Optimization

Every included context element should be explainable.

Professionals should understand why a document influenced a recommendation.

---

## Deterministic Construction

Given identical organizational state and inputs, the Context Builder should produce equivalent context.

Implementation randomness should not alter organizational reasoning.

---

# Context Sources

The Context Builder may assemble context from:

* Vision
* Mission
* Constitution
* Engineering Principles
* RFCs
* TDSs
* TDRs
* Engineering Standards
* Knowledge Objects
* Executive Memory
* Decisions
* Blueprints
* Capabilities
* Mission history
* Experience Records
* Organizational metrics

Conversation history is considered supplemental context rather than authoritative knowledge.

---

---

# Context Construction Pipeline

The Context Builder follows these stages.

## Request Analysis

Determine:

* requesting Professional;
* requested capability;
* organizational objective;
* execution scope.

---

## Context Discovery

Locate relevant organizational assets.

Priority follows the authoritative hierarchy.

---

## Context Validation

Remove:

* deprecated knowledge;
* superseded decisions;
* conflicting standards;
* obsolete artifacts.

Only valid organizational knowledge proceeds.

---

## Context Composition

Assemble context into a structured representation suitable for downstream reasoning.

Composition should preserve:

* references;
* authority;
* ordering;
* provenance.

---

## Context Delivery

Deliver the constructed context to the requesting subsystem.

Consumers should not modify authoritative content.

---

# Context Provenance

Every context package should preserve:

* source documents;
* document versions;
* inclusion rationale;
* authority level;
* construction timestamp.

Context should remain fully explainable.

---

# Relationship to the Knowledge Graph

The Context Builder queries the Knowledge Graph to identify relevant relationships among:

* Decisions;
* Missions;
* Blueprints;
* Capabilities;
* Professionals;
* Knowledge Objects.

The graph improves context relevance while preserving organizational consistency.

---

# Relationship to Executive Memory

Executive Memory provides high-level strategic context.

The Context Builder supplements Executive Memory with detailed authoritative references when required.

---

# Relationship to the AI Abstraction Layer

The Context Builder operates before AI invocation.

The AI Abstraction Layer consumes constructed context but does not influence its composition.

This separation preserves provider independence.

---

# Governance

Changes to context prioritization require architectural review.

Context construction rules are organizational policy rather than implementation preferences.

Unauthorized context modification is prohibited.

---

# Alternatives Considered

## Full Conversation Replay

Rejected because conversations are noisy, temporary, and difficult to govern.

---

## Vector Search Only

Rejected because semantic similarity alone does not preserve organizational authority.

---

## Provider Memory

Rejected because provider memory is implementation-dependent and not organizationally governed.

---

# Consequences

Positive outcomes include:

* consistent reasoning;
* lower token consumption;
* stronger explainability;
* improved architectural compliance;
* reduced hallucination risk;
* durable organizational memory.

Trade-offs include:

* centralized governance;
* context construction complexity;
* metadata maintenance.

These trade-offs are accepted because they substantially improve organizational intelligence.
