# RFC-0036 — Knowledge Query Engine

**RFC Number:** RFC-0036

**Title:** Knowledge Query Engine

**Status:** Approved

**Version:** 1.0.0

**Authors:** ForgeOS Architecture Office

**Last Updated:** 2026-08-01

---

# Abstract

This RFC defines the Knowledge Query Engine (KQE), the subsystem responsible for retrieving authoritative organizational knowledge throughout ForgeOS.

The Knowledge Query Engine provides a unified query interface across all organizational knowledge sources while preserving governance, provenance, explainability, and deterministic behavior.

Unlike conventional search systems, the Knowledge Query Engine answers organizational questions by reasoning over governed knowledge rather than simply locating documents.

---

# Motivation

As ForgeOS grows, organizational knowledge expands across:

* RFCs;
* Technical Design Specifications;
* Engineering Standards;
* Blueprints;
* Knowledge Objects;
* Executive Memory;
* Engineering Memory;
* Decisions;
* Mission history;
* Experience records;
* Organization DNA;
* Organizational Health.

Without a unified retrieval subsystem, knowledge becomes fragmented and difficult to reuse.

ForgeOS therefore introduces a dedicated organizational query engine.

---

# Problem Statement

Conventional document search suffers from:

* duplicated results;
* conflicting information;
* lack of authority ranking;
* poor traceability;
* disconnected organizational relationships.

Organizations require deterministic retrieval from governed knowledge.

---

# Goals

The Knowledge Query Engine shall:

* retrieve authoritative knowledge;
* preserve provenance;
* rank results by organizational authority;
* support semantic organizational queries;
* integrate with the Knowledge Graph;
* remain implementation independent.

---

# Non-Goals

The Knowledge Query Engine does not define:

* search indexes;
* vector databases;
* embedding models;
* LLM prompting;
* storage technologies.

Those belong to implementation specifications.

---

# Decision

ForgeOS adopts the Knowledge Query Engine as the authoritative retrieval subsystem.

Every Professional, Executive subsystem, and AI provider shall obtain organizational knowledge through the Knowledge Query Engine rather than directly accessing repositories.

---

# Query Principles

## Authority Before Similarity

Approved organizational knowledge outranks semantically similar but ungoverned content.

---

## Explainability Before Convenience

Every retrieved result shall include its authoritative source and retrieval rationale.

---

## Deterministic Retrieval

Equivalent organizational state and equivalent queries should produce equivalent retrieval results.

---

## Organization Before Documents

Queries target organizational knowledge rather than individual files.

---

## Knowledge Reuse

Existing knowledge shall always be preferred over creating duplicate knowledge.

---

# Query Pipeline

The Knowledge Query Engine follows this conceptual pipeline.

```text
Query
   ↓
Intent Analysis
   ↓
Authority Resolution
   ↓
Knowledge Graph Traversal
   ↓
Semantic Matching
   ↓
Ranking
   ↓
Validation
   ↓
Knowledge Package
```

---

# Query Types

The engine supports multiple query categories.

## Fact Queries

Retrieve authoritative facts.

Example:

* "What is a Mission?"

---

## Relationship Queries

Traverse organizational relationships.

Example:

* "Which Capabilities support Blueprint X?"

---

## Historical Queries

Retrieve organizational evolution.

Example:

* "Why was RFC-0016 introduced?"

---

## Decision Queries

Locate executive decisions and architectural rationale.

---

## Strategic Queries

Retrieve organizational strategy and planning knowledge.

---

## Engineering Queries

Retrieve implementation guidance, engineering standards, architecture decisions, and reusable technical knowledge.

---

# Knowledge Sources

The engine may retrieve information from:

* Vision;
* Mission;
* Constitution;
* RFCs;
* TDSs;
* ADRs;
* TDRs;
* Engineering Standards;
* Executive Memory;
* Engineering Memory;
* Knowledge Objects;
* Blueprints;
* Capabilities;
* Skills;
* Competencies;
* Mission history;
* Organization Health;
* Organization DNA.

Conversation history is treated as contextual rather than authoritative.

---

# Query Ranking

Ranking considers:

* authority level;
* governance status;
* document version;
* organizational relevance;
* relationship distance;
* semantic relevance;
* recency where appropriate.

Authority remains the primary ranking signal.

---

# Knowledge Package

Every successful query returns a Knowledge Package containing:

* requested answer;
* supporting references;
* authoritative documents;
* relationship context;
* confidence assessment;
* provenance;
* retrieval explanation.

The package is suitable for direct consumption by downstream systems.

---

# Relationship to the Knowledge Graph

The Knowledge Graph provides semantic relationships used during retrieval.

The Knowledge Query Engine interprets those relationships to construct meaningful answers.

---

# Relationship to the Context Builder

The Context Builder invokes the Knowledge Query Engine during context construction.

The Query Engine retrieves.

The Context Builder composes.

This separation preserves architectural clarity.

---

# Relationship to Organizational Search

The Organizational Search Engine locates organizational assets.

The Knowledge Query Engine answers organizational questions.

Search discovers.

Query explains.

---

# Relationship to AI Abstraction Layer

AI providers never retrieve organizational knowledge directly.

They receive Knowledge Packages produced by the Knowledge Query Engine.

This preserves provider independence.

---

# Governance

Query behavior shall remain:

* deterministic;
* explainable;
* traceable;
* versioned.

Retrieval policies require architectural governance.

---

# Alternatives Considered

## Keyword Search

Rejected because keywords cannot adequately represent organizational semantics.

---

## Vector Search Only

Rejected because semantic similarity alone cannot preserve governance and authority.

---

## Repository Browsing

Rejected because repositories expose storage organization rather than organizational knowledge.

---

# Consequences

Positive outcomes include:

* unified organizational retrieval;
* stronger explainability;
* reduced knowledge duplication;
* deterministic organizational reasoning;
* improved AI alignment;
* lower executive cognitive load.

Trade-offs include:

* richer metadata;
* governance overhead;
* query planning complexity.

These trade-offs are accepted because they strengthen organizational intelligence.
