# Purpose

This Technical Design Specification defines the implementation architecture of ForgeOS Core.

Unlike the architectural RFCs, this document specifies concrete implementation boundaries, runtime responsibilities, module ownership, dependency rules, communication patterns, and persistence responsibilities.

Its objective is to enable a Senior Software Engineer to implement ForgeOS Core without inventing architecture.

---

# Scope

This document specifies:

- system decomposition;
- runtime components;
- module responsibilities;
- component interfaces;
- dependency rules;
- data flow;
- event flow;
- persistence ownership;
- extension points.

Technology selection is intentionally excluded and documented separately in Technology Decision Records (TDRs).

---

# Architectural Principles

The implementation shall preserve the following architectural invariants.

1. Organization is the primary domain boundary.
2. Knowledge is the primary persistent asset.
3. Missions drive execution.
4. Processes implement Missions.
5. AI providers are replaceable infrastructure.
6. Business logic never depends directly on UI.
7. Business logic never depends directly on LLM providers.
8. Persistence is abstracted behind repositories.
9. Every domain module owns its own business rules.
10. Cross-module communication occurs through published interfaces or domain events.

---

# System Context

ForgeOS Core is composed of five logical layers.

```text
Presentation
        │
Application
        │
Domain
        │
Infrastructure
        │
Platform
```

Dependencies always point downward.

No lower layer may depend on a higher layer.

---

# Runtime Modules

## Presentation Layer

Responsibilities:

- Desktop UI
- User interaction
- Visualization
- Command dispatch
- View state

May depend on:

- Application Layer

Must never depend on:

- Domain
- Infrastructure
- Persistence

---

## Application Layer

Responsibilities:

- Use cases
- Command handlers
- Query handlers
- Workflow orchestration
- Transaction boundaries
- Authorization coordination

May depend on:

- Domain

Must never depend on:

- UI
- Storage implementation
- LLM implementation

---

## Domain Layer

Responsibilities:

- Organizations
- Missions
- Processes
- Knowledge
- Capabilities
- Professionals
- Decisions
- Rules
- Policies

The Domain Layer owns all business rules.

No infrastructure logic belongs here.

---

## Infrastructure Layer

Responsibilities:

- Persistence
- Event Bus
- Search
- AI Providers
- Files
- Networking
- Plugins

Infrastructure implements interfaces owned by the Domain.

---

## Platform Layer

Responsibilities:

- OS Integration
- Configuration
- Logging
- Diagnostics
- Dependency Injection
- Runtime Bootstrap

Platform contains no business logic.

# Application Services

Application Services coordinate work between domain modules.

Examples include:

- Create Mission
- Execute Mission
- Promote Knowledge
- Record Decision
- Build Context
- Evaluate Organization Health
- Generate Executive Dashboard

Application Services do not contain business rules.

---

# Repository Interfaces

Each aggregate root owns its repository interface.

Examples:

- OrganizationRepository
- MissionRepository
- KnowledgeRepository
- ProcessRepository
- ProfessionalRepository

Repository interfaces belong to the Domain.

Implementations belong to Infrastructure.

---

# Event Model

ForgeOS uses domain events for cross-module communication.

Representative events:

- MissionCreated
- MissionStarted
- MissionCompleted
- KnowledgePromoted
- DecisionApproved
- OrganizationUpdated
- BlueprintPublished
- CapabilityAdded

Domain modules publish events.

Subscribers remain implementation independent.

---

# Command Flow

```text
UI
 ↓
Application Command
 ↓
Domain
 ↓
Repository
 ↓
Event Publication
 ↓
Subscribers
```

---

# Query Flow

```text
UI
 ↓
Application Query
 ↓
Repository
 ↓
Read Model
 ↓
UI
```

Queries shall not modify domain state.

---

# Persistence Responsibilities

Each domain module owns its persistence model.

Shared database tables across domain modules are prohibited.

Relationships between modules occur through identifiers and domain events rather than direct table coupling.

---

# Dependency Rules

Allowed:

Presentation → Application

Application → Domain

Infrastructure → Domain Interfaces

Platform → Infrastructure

Forbidden:

Presentation → Infrastructure

Presentation → Database

Domain → UI

Domain → LLM

Domain → Database

Infrastructure → Presentation

Cross-domain circular dependencies

---

# AI Boundary

AI providers are external services.

The Domain never communicates directly with an AI provider.

Instead:

Domain

→ Context Builder

→ AI Abstraction Layer

→ Provider Adapter

This preserves provider independence.

---

# Plugin Boundary

Plugins may:

- register commands;
- register queries;
- contribute domain services;
- contribute UI extensions.

Plugins shall not modify existing domain behavior directly.

Extension occurs through published interfaces only.

---

# Configuration Boundary

Configuration shall be injected into Infrastructure and Platform only.

Business rules shall never depend on configuration files.

---

# Error Handling

Errors are categorized as:

- Validation
- Business Rule
- Infrastructure
- External Provider
- Security
- Unexpected

Business errors originate in the Domain.

Infrastructure errors originate outside the Domain.

---

# Observability

Every Application Service shall emit:

- structured logs;
- execution duration;
- domain events;
- error classification.

Observability shall not alter business behavior.

---

# Security Boundary

Authentication and authorization occur before Application Services execute.

Domain logic assumes authenticated execution and validates business authorization rules.

---

# Extension Points

Stable extension points include:

- AI Providers
- Search Providers
- Storage Providers
- Plugin Modules
- Import/Export Providers
- Notification Providers

These extension points shall remain interface-driven.

---

# Architectural Invariants

The following constraints are mandatory:

- Business logic resides only in the Domain.
- Infrastructure depends on abstractions.
- Domain never depends on Infrastructure.
- Every persistent aggregate has one owning module.
- Every cross-module interaction is explicit.
- Every external integration passes through Infrastructure.
- Every AI interaction passes through the AI Abstraction Layer.

Violation of these invariants requires architectural review.

---

# Implementation Readiness Checklist

A ForgeOS Core implementation shall be able to identify:

- runtime layers;
- module ownership;
- dependency directions;
- repository boundaries;
- event flow;
- command flow;
- query flow;
- persistence ownership;
- extension mechanisms.

This document intentionally does not specify programming language, desktop framework, or storage engine. Those implementation choices are defined by corresponding Technology Decision Records.
