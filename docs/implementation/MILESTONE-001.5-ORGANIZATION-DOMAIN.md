# Milestone 001.5 — Organization Domain Foundation

**Status:** Approved — Scope Authorized; Execution Pending  
**Scope:** Organization Domain Foundation scope definition for the Create Organization capability. This document authorizes no source code, dependency, workspace, crate, or architecture change. It defines the approved domain-facing scope that the next implementation step will execute.

---

# 1. Objective

Implement the **Organization Domain Foundation** inside the `forgeos-organization-domain` crate: the domain-owned layer of the Create Organization capability, consisting of the Organization aggregate, its approved value objects and required internal entities, the Domain-owned `OrganizationRepository` contract, the immutable `OrganizationCreated` domain event, the approved domain error model, and deterministic domain tests.

This milestone establishes the first executable domain boundary of ForgeOS. It does not create infrastructure, application, platform, persistence, IPC, or presentation behavior.

# 3. In-Scope Domain Concepts

All creation semantics are governed by the approved `MILESTONE-001-DOMAIN-DECISIONS.md` (Version 1.0.0). The Domain Foundation shall implement:

## 3.1 Value objects

* `OrganizationId` — immutable, globally unique, generated by the aggregate; callers never supply it.
* `OrganizationName` — required, at least one non-whitespace character, preserved as supplied.
* `OrganizationType` — required, at least one non-whitespace character, preserved as supplied (no case folding, normalization, length limit, or type enumeration in Milestone 1.5).
* `OrganizationStatus` — initial observable status `Active`.
* `OrganizationVersion` — initial value `1`.

Value objects are immutable and compare by value.

## 3.2 Organization aggregate

* Sole aggregate root of the Organization bounded context and sole mutation boundary for organizational state.
* Creation behavior: generates its own identity; establishes the supplied name and type; initializes with no capabilities, hierarchy members, or additional configuration; records the `OrganizationCreated` event; returns as `Active` with version `1`.
* Exposes behavior rather than mutable internal state.
* Enforces the approved creation invariants (validation rules and the singleton rule of the approved decision package).

## 3.3 Internal entities

`OrganizationProfile`, `OrganizationHierarchy`, `OrganizationCapability`, and `OrganizationClassification` are implemented only to the extent required by the approved Create Organization creation semantics. No entity behavior or field is added by assumption.

## 3.4 Repository contract

* `OrganizationRepository` is Domain-owned and supports create, retrieve, update, archive, existence verification, and optimistic concurrency.
* The contract must not expose persistence technology.
* Milestone 1.5 defines the trait only; no infrastructure implementation is created.

## 3.5 Domain events

* `OrganizationCreated` is an immutable record of the completed creation business fact.
* Event dispatch after successful transaction commit remains governed by ISP-0005 and ISP-0006; no consumer or dispatcher is in scope here.

## 3.6 Domain errors

* Domain validation errors for missing or whitespace-only `name` / `organization_type`.
* Business-rule failure `OrganizationAlreadyExists` for the singleton constraint.
* Structured unexpected error boundary.
* No infrastructure, persistence, or platform error types enter the Domain.

## 3.7 Domain tests

* Pure, deterministic, dependency-free unit tests per ISP-0009 and ISP-0010, colocated with the `forgeos-organization-domain` crate.
* Coverage: aggregate creation semantics, value-object immutability, invariant enforcement, singleton business rule, and `OrganizationCreated` emission.

# 7. Implementation Acceptance Criteria

1. `forgeos-organization-domain` compiles with no dependencies beyond the Rust standard library, unless an approved exception is recorded.
2. All approved value objects exist, are immutable, and compare by value.
3. Aggregate creation matches the approved decision package: internally generated identity; established name and type; no capabilities, hierarchy, or configuration; `Active` status; version `1`; `OrganizationCreated` recorded.
4. Creation invariants are enforced: validation of `name` and `organization_type` (non-whitespace required) and the exactly-one-Organization singleton rule surfaced as `OrganizationAlreadyExists`.
5. `OrganizationRepository` is Domain-owned and exposes create, retrieve, update, archive, existence verification, and optimistic concurrency without exposing persistence technology.
6. `OrganizationCreated` is an immutable business fact with stable fields.
7. Domain errors follow the approved error model: Validation, Business Rule (`OrganizationAlreadyExists`), and Unexpected; no infrastructure error types leak into the Domain.
8. Domain tests are pure, deterministic, and dependency-free, covering creation semantics, immutability, invariant enforcement, and event emission per ISP-0009 and ISP-0010.
9. The Organization Domain crate depends only on approved shared/value-object/event contracts (none currently required); no Infrastructure, Application, Platform, Tauri, SQLx, or Serde dependency exists.
10. No workspace member manifest, crate boundary, or dependency edge changes beyond the approved `forgeos-organization-domain` package.
