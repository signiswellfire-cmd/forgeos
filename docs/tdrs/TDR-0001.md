# TDR-0001 — Programming Language

**TDR Number:** TDR-0001

**Title:** Programming Language

**Status:** Approved

**Version:** 1.0.0

**Related TDS:** TDS-0001 — System Architecture

---

# Purpose

This Technology Decision Record selects the primary implementation language for ForgeOS Core.

This decision applies to the core runtime, domain model, application services, infrastructure layer, plugin SDK, and shared libraries.

User interface technologies are addressed separately.

---

# Context

TDS-0001 defines several architectural constraints.

ForgeOS requires:

- long-lived desktop execution;
- modular architecture;
- strong compile-time correctness;
- replaceable infrastructure providers;
- efficient local execution;
- concurrent background processing;
- plugin extensibility;
- low runtime overhead;
- cross-platform support;
- long-term maintainability.

The programming language must reinforce these architectural goals rather than compensate for weaknesses in the architecture.

---

# Decision

ForgeOS Core shall be implemented in **Rust**.

Rust becomes the primary implementation language for:

- Domain Layer
- Application Layer
- Infrastructure Layer
- Platform Layer
- Shared libraries
- Plugin SDK
- Command-line utilities
- Background services

The user interface technology is intentionally excluded from this decision and is specified separately.

---

# Decision Drivers

The selected language shall support:

- memory safety without garbage collection;
- deterministic performance;
- strong type safety;
- explicit ownership;
- high concurrency;
- predictable resource management;
- excellent cross-platform support;
- modern tooling;
- mature package management;
- long-term ecosystem stability.

---

# Architectural Alignment

Rust aligns with the architectural principles established in TDS-0001.

## Layer Isolation

Rust crates naturally support explicit module boundaries.

The compiler reinforces dependency rules defined by the architecture.

---

## Domain Integrity

Rich type systems allow business rules to be encoded directly within the domain model.

Compile-time validation reduces runtime defects.

---

## Infrastructure Abstraction

Traits provide stable abstraction boundaries between domain interfaces and infrastructure implementations.

Infrastructure remains replaceable without modifying business logic.

---

## Concurrency

ForgeOS performs:

- background indexing;
- knowledge processing;
- event handling;
- synchronization;
- AI orchestration.

Rust provides efficient concurrency primitives while preventing common synchronization defects.

---

## Long-Term Maintainability

Compile-time correctness reduces maintenance cost throughout the project lifecycle.

---

# Repository Organization

Rust implementation shall follow a Cargo workspace structure.

Representative top-level crates include:

```text
forgeos-core/
forgeos-domain/
forgeos-application/
forgeos-infrastructure/
forgeos-platform/
forgeos-ai/
forgeos-plugin-api/
forgeos-cli/
```

Additional crates may be introduced provided architectural dependency rules remain satisfied.

---

# Architectural Constraints

The following constraints apply.

Business logic shall never depend upon infrastructure crates.

Infrastructure crates may depend upon domain traits.

Application crates coordinate domain modules.

Platform crates provide runtime services only.

Circular crate dependencies are prohibited.

---

# Build System

The standard build system shall be:

- Cargo

The workspace shall provide:

- reproducible builds;
- dependency locking;
- workspace-wide testing;
- linting;
- documentation generation.

---

# Testing

Rust's native testing framework shall be used for:

- unit tests;
- integration tests;
- documentation tests.

Additional testing frameworks may supplement but not replace the standard testing model.

---

# Error Handling

Recoverable errors shall use explicit result types.

Unexpected failures shall be propagated through structured error handling rather than uncontrolled panics.

Error types shall remain domain-specific where practical.

---

# Logging

Structured logging shall be used throughout the runtime.

Logging implementations remain infrastructure concerns.

---

# Plugin Support

The language shall support a stable plugin abstraction through published ForgeOS interfaces.

Plugin implementation details are defined separately.

---

# Alternatives Considered

## C#

Advantages:

- mature desktop ecosystem;
- excellent tooling;
- strong language features.

Rejected because garbage collection introduces runtime characteristics inconsistent with the desired deterministic execution model.

---

## Kotlin

Advantages:

- expressive language;
- excellent JVM ecosystem.

Rejected because JVM runtime requirements introduce unnecessary deployment complexity for a local-first desktop platform.

---

## Go

Advantages:

- simple language;
- strong concurrency support.

Rejected because the type system and abstraction mechanisms provide less flexibility for the rich domain modeling required by ForgeOS.

---

## TypeScript

Advantages:

- rapid development;
- broad ecosystem.

Rejected because critical domain logic should benefit from stronger compile-time guarantees and native execution.

---

## C++

Advantages:

- high performance;
- native execution.

Rejected because memory safety and maintainability objectives outweigh the additional control provided by manual memory management.

---

# Consequences

Positive consequences:

- strong architectural enforcement;
- memory safety;
- deterministic runtime behavior;
- excellent cross-platform support;
- efficient concurrency;
- low resource consumption.

Trade-offs:

- steeper learning curve;
- longer initial onboarding;
- explicit ownership model;
- smaller hiring pool compared to mainstream enterprise languages.

These trade-offs are accepted because they reinforce the long-term architectural objectives of ForgeOS.

---

# Future Considerations

Future TDRs may define:

- foreign function interface policy.

These decisions remain independent of the programming language choice.
