# TDR-0002 — Desktop Framework

**TDR Number:** TDR-0002

**Title:** Desktop Framework

**Status:** Approved

**Version:** 1.0.0

**Related TDS:** TDS-0001 — System Architecture

**Related TDR:** TDR-0001 — Programming Language

---

# Purpose

This Technology Decision Record selects the desktop application framework for ForgeOS.

The desktop framework provides the host runtime responsible for:

- window management;
- lifecycle management;
- frontend/backend communication;
- native operating system integration;
- application packaging;
- secure execution.

Business logic remains implemented within ForgeOS Core and is independent of the selected desktop framework.

---

# Context

TDS-0001 establishes that:

- Presentation depends only upon the Application Layer.
- Business logic remains independent of UI technologies.
- Infrastructure is replaceable.
- ForgeOS is a local-first desktop application.
- Cross-platform support is mandatory.

Following TDR-0001, the implementation language is Rust.

The desktop framework should therefore maximize integration with Rust while minimizing architectural complexity.

---

# Decision

ForgeOS shall use **Tauri 2.x** as the primary desktop application framework.

Tauri becomes responsible for:

- native application hosting;
- application lifecycle;
- frontend/backend IPC;
- native menus;
- system tray integration;
- window management;
- secure filesystem access;
- packaging and distribution.

Tauri is not responsible for business logic.

All business logic remains inside ForgeOS Core.

---

# Decision Drivers

The selected framework shall provide:

- first-class Rust support;
- native desktop execution;
- low memory consumption;
- secure IPC;
- cross-platform packaging;
- operating system integration;
- long-term ecosystem stability;
- plugin support.

---

# Architectural Alignment

## Separation of Concerns

Tauri naturally separates:

Frontend

↓

IPC

↓

Rust Backend

This aligns directly with the layered architecture defined by TDS-0001.

---

## Local-First Architecture

ForgeOS executes entirely on the local workstation.

Tauri supports local execution without requiring an embedded browser server or cloud runtime.

---

## Native Performance

Business logic executes directly within Rust.

The desktop framework remains a presentation host rather than an application runtime.

---

## Security

Tauri provides explicit IPC boundaries.

Backend functionality is exposed only through approved commands.

The frontend cannot directly access internal application state.

---

# Runtime Architecture

The desktop runtime consists of:

```text
Frontend
      │
      │ IPC
      ▼
Tauri Runtime
      │
      ▼
forgeos-core
      │
      ▼
Infrastructure
```

The Tauri runtime owns only desktop orchestration.

ForgeOS Core owns all organizational behavior.

---

# Frontend Responsibilities

The frontend shall own:

- navigation;
- visual presentation;
- user interaction;
- client-side state;
- visualization.

The frontend shall never contain:

- domain logic;
- persistence logic;
- workflow rules;
- governance rules.

---

# Backend Responsibilities

The Rust backend shall own:

- application services;
- domain model;
- repositories;
- knowledge processing;
- Mission execution;
- search;
- AI orchestration;
- event handling.

---

# IPC Rules

Frontend-to-backend communication shall occur exclusively through published Tauri commands.

Commands:

- validate inputs;
- invoke application services;
- return DTOs.

Domain entities shall never cross the IPC boundary directly.

---

# Data Transfer Objects

Communication across IPC shall use dedicated DTOs.

DTOs:

- are immutable;
- contain no business behavior;
- are versionable;
- remain independent of domain entities.

---

# Window Model

Initial MVP windows:

- Main Workspace
- Settings
- About

Future modules may contribute additional windows through the plugin system.

---

# Plugin Integration

Desktop plugins may provide:

- menus;
- commands;
- panels;
- settings pages;
- visual components.

Plugins shall not bypass ForgeOS Core.

All business operations remain routed through Application Services.

---

# Packaging

The desktop framework shall support:

- Windows
- macOS
- Linux

Packaging configuration remains infrastructure and deployment concern.

---

# Alternatives Considered

## Electron

Advantages:

- mature ecosystem;
- extensive community;
- broad library support.

Rejected because:

- higher memory consumption;
- larger application footprint;
- business logic would require additional integration layers with Rust.

---

## Flutter Desktop

Advantages:

- excellent UI capabilities;
- strong cross-platform consistency.

Rejected because it introduces an additional runtime and language ecosystem without improving the architectural objectives of ForgeOS Core.

---

## Qt

Advantages:

- mature native desktop framework;
- high performance.

Rejected because Rust integration is less direct and the framework introduces additional complexity for the MVP.

---

## Native Rust GUI Frameworks

Examples include egui, Dioxus, and Slint.

Rejected for the MVP because ecosystem maturity and tooling remain less stable than Tauri for a complex desktop application with web-based interface requirements.

These frameworks may be evaluated in future architectural reviews.

---

# Consequences

Positive consequences:

- tight integration with Rust;
- lightweight desktop runtime;
- native packaging;
- strong process isolation;
- reduced memory consumption;
- clear frontend/backend separation.

Trade-offs:

- frontend requires web technologies;
- IPC contracts require explicit maintenance;
- desktop plugins must conform to Tauri extension model.

These trade-offs are accepted because they reinforce the architectural goals established by TDS-0001.
